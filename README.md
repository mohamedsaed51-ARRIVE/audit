# ARRIVE AUDIT CONTROL TOWER (V3)

نظام لوحة تحكم للتدقيق التشغيلي الداخلي في **ARRIVE** (شركة شحن وتوصيل مصرية)، مبني على **Google
Apps Script** (Backend، ملف `appsscript/Code.gs`) + **Google Sheets** (قاعدة البيانات) + صفحة واجهة
واحدة (`dashboard/index.html`).

## 1) الغرض من النظام

تسجيل ومتابعة عمليات التدقيق التشغيلي اليومي، وحساب مؤشرات الأداء (KPIs)، وتوليد تقارير تنفيذية،
وإدارة صلاحيات فريق التدقيق نفسه — كل ذلك من واجهة واحدة متصلة مباشرة بجدول Google Sheets كمصدر
للبيانات.

## 2) النطاق: مخصَّص حصريًا لموظفي قسم التدقيق الداخلي

**لا يوجد ولا يُقصَد أن يوجد أي دور لموظفي الفروع، أو Operations، أو Customer Service، أو أي طرف
خارجي.** كل الأدوار الخمسة المتاحة (راجع القسم 12) هي أدوار داخل قسم التدقيق فقط. الدور الذي كان
يُسمَّى سابقًا "Branch Manager" أُعيدت تسميته إلى **Senior Auditor** — بنفس الصلاحيات بالضبط، ولا علاقة
له بأي موظف فرع فعلي.

## 3) وظائف الرقابة السبع

كل وظيفة رقابة لها تاب مخصَّص في جدول Google Sheets:

| المفتاح | الاسم |
|---|---|
| Morning | المطابقة الصباحية |
| Returns | مطابقة المرتجعات |
| Scrub | مسح الحالات |
| Transfer | التحويلات |
| Issues | المشاكل اليومية |
| Penalty | الجزاءات |
| Overdue | الحالات المتأخرة |

لكل نوع نموذج إدخال/تعديل مخصَّص في الواجهة، وبطاقة KPI في لوحة التحكم الرئيسية، ووزنه الخاص في شاشة
التقارير.

## 4) فتح لوحة التحكم دون إعادة إدخال الرابط

عند فتح `dashboard/index.html` لأول مرة، تُطلَب منك رابط الـWeb App الخاص بالـBackend (راجع القسم 5).
بعد إدخاله مرة واحدة، يُحفَظ في `localStorage` الخاص بالمتصفح (`arrive_api_url`) — لن يُطلَب منك مرة
أخرى على نفس الجهاز/المتصفح ما لم تمسح بيانات الموقع يدويًا.

## 5) حفظ رابط الـBackend (Web App URL)

بعد نشر `appsscript/Code.gs` كـWeb App من محرِّر Google Apps Script (Deploy → New deployment → Web
app)، الصق الرابط الناتج في الحقل المخصَّص أعلى الصفحة عند أول فتح. لا يُخزَّن هذا الرابط في أي ملف
داخل هذا المستودع — فقط في متصفحك المحلي.

## 6) إعدادات النظام (Settings)

تُدار من تاب "الإعدادات" في جدول Google Sheets مباشرة (الأهداف الرقمية لكل نوع رقابة، فئات عمر الحالات
المتأخرة، قوائم القيم المعتمدة، حالة `auth_enabled`)، وتُعرَض للقراءة في شاشة "الإعدادات" بالواجهة.
تغيير أي قيمة يتطلب تحرير الشيت مباشرة حاليًا (لا توجد شاشة تحرير إعدادات عامة داخل الواجهة بعد، باستثناء
إدارة الفروع والموظفين الموضَّحة أدناه).

## 7) معرّف الفرع (Branch ID)

معرّف داخلي ثابت (مثل `BR-001`) يُنشأ تلقائيًا عند إضافة فرع، ولا يتغيّر أبدًا حتى لو أُعيدت تسمية
الفرع لاحقًا — يُستخدَم للربط الداخلي (الصلاحيات، Branch Scope، سجل العمليات)، بينما اسم الفرع
المعروض للمستخدم قابل للتغيير بحرية. راجع `docs/branch-id-migration.md` للتفصيل الكامل.

## 8) إدارة الفروع

من شاشة الإعدادات → إدارة الفروع (تتطلب صلاحية `manageBranches` — Administrator فقط حاليًا): إضافة
فرع جديد، إعادة تسمية فرع موجود (الاسم فقط، الـBranch ID لا يتغيّر)، تعطيل فرع (لا حذف — التعطيل يمنع
اختياره في سجلات جديدة دون فقدان تاريخه).

## 9) أداة معاينة هجرة الفروع (Branch Migration Preview)

**أداة قراءة فقط بالكامل — لا تكتب أي شيء على أي شيت.** تفحص السجلات القديمة في التابات السبعة وتصنِّف
كل سجل حسب مدى ربطه بمعرّف فرع صحيح (مرتبط/غير مرتبط/يحتاج مراجعة/تكرار اسم/اسم غير معروف)، وتُرجع
تقريرًا JSON. **لا توجد بعد أداة تنفّذ هجرة فعلية** — راجع `docs/branch-id-migration.md` لكل التفاصيل،
بما فيها كيفية إنشاء نسخة احتياطية قبل أي هجرة فعلية مستقبلية.

## 10) إدارة موظفي التدقيق (Employees Management)

من شاشة الإعدادات → إدارة الموظفين (تتطلب `manageEmployees`): إضافة موظف (اسم كامل، اسم مستخدم، كلمة
مرور، دور، نطاق فروع)، تعديل بيانات موظف (بما فيها الدور ونطاق الفروع)، تعطيل حساب. **لا حذف لأي حساب
موظف.** منتقي الفروع يظهر دائمًا؛ خيار "منح كل الفروع" منفصل، ولا يظهر إلا للأدوار المصرَّح لها، ويتطلب
تأكيدًا إضافيًا قبل الحفظ. لا يمكن لأي مستخدم (حتى Administrator) تعديل دوره أو نطاق فروعه الخاص من
حسابه نفسه.

## 11) تسجيل الدخول

اسم مستخدم + كلمة مرور. أول حساب Administrator يُنشأ عبر شاشة "تهيئة النظام لأول مرة" (Bootstrap) —
تعمل مرة واحدة فقط قبل وجود أي حساب. بعد 5 محاولات فاشلة متتالية، يُقفَل الحساب مؤقتًا 15 دقيقة.

## 12) الأدوار والصلاحيات (ملخّص — التفصيل الكامل في `docs/permissions-matrix.md`)

| # | الدور |
|---|---|
| 1 | Administrator |
| 2 | Audit Manager |
| 3 | Senior Auditor |
| 4 | Auditor |
| 5 | Audit Viewer |

هذه القائمة **نهائية ومصدرها الوحيد** `backend/schema.json` (`role_permissions`). لا يُضاف دور جديد
ولا يُغيَّر تعريف دور موجود إلا بتحديث ذلك الملف أولًا ثم إعادة تضمينه في `Code.gs`.

## 13) نطاق الفروع (Branch Scope)

آلية داخلية لتحديد الفروع التي يُسمح لموظف تدقيق بمراجعة بياناتها — **غير مرتبطة بتوظيف فعلي في أي
فرع** (لا يوجد موظفو فروع في هذا النظام أصلًا). كل دور نطاقه إما `"all"` (Administrator فقط، على مستوى
الدور) أو `"own"` (البقية — مقيَّدون بفروعهم المخصَّصة فقط، مع إمكانية منح "كل الفروع" صراحةً لبعض
الأدوار فقط — راجع القسم التالي). يُفرَض هذا في الـBackend فعليًا لكل عمليات القراءة والكتابة وسجل
العمليات، وليس بإخفاء عناصر الواجهة فقط.

## 14) ALL Branches (الوصول لكل الفروع)

لا يُمنح تلقائيًا لأي أحد. Administrator يملكه دائمًا لأغراض إدارة النظام. Audit Manager يمكن منحه
إياه، لكن فقط بتفويض صريح لكل حساب على حدة (وليس افتراضيًا). Senior Auditor وAuditor وAudit Viewer
**ممنوعون كليًا** من الحصول عليه مهما فعل من يدير الحسابات. القيمة الوحيدة المقبولة لمنحه هي اختيار
صريح من الواجهة (مع تأكيد إضافي) — لا فراغ ولا قائمة فارغة تُفسَّر كذلك أبدًا.

## 15) سجل العمليات (Audit Log)

يسجّل كل عملية حساسة (دخول/خروج/حفظ/تعديل/إدارة فروع/إدارة موظفين/تشغيل أداة المعاينة) مع الوقت
والمستخدم والنتيجة. تعديلات الموظفين (دور/نطاق فروع/اسم) تُسجَّل بصيغة JSON منظَّمة تتضمن القيمة
القديمة والجديدة — **بلا أي كلمة مرور أو Hash إطلاقًا**. من يملك `viewAuditLog` فقط يراه (Administrator/
Audit Manager/Senior Auditor)، وأدوار "own" ترى عمليات فروعها فقط.

## 16) تشغيل الاختبارات

```
npm install
npm run test:all
```

أو كل مجموعة على حدة (`npm run test:harness`، `test:parity`، `test:admin`، `test:security`،
`test:migration`، `test:branch-scope`، `test:session-ttl`، `test:branch-empty-fix`، `test:browser`،
`test:browser-admin`، `test:xss`) — راجع `package.json` للقائمة الكاملة.

## 17) الفرق بين اختبار Sandbox واختبار Live Integration الحقيقي

**كل الاختبارات في هذا المستودع (321 اختبارًا في آخر تشغيل موثَّق) هي Sandbox أو Playwright ضد نفس
الـSandbox:**
- **Sandbox** (Node.js): يُشغِّل ملف `appsscript/Code.gs` الفعلي (السطر بالسطر، عبر وحدة `vm` في
  Node.js) ضد محاكاة داخلية لـGoogle Sheets/CacheService/Utilities — يثبت أن منطق الكود متّسق داخليًا.
- **Playwright**: متصفح حقيقي، لكن موجَّه ضد نفس محاكاة الـSandbox (وليس Web App منشورًا فعليًا) —
  يثبت أن الواجهة تتفاعل بشكل صحيح مع نفس المنطق.
- **Live Integration (Google Apps Script + Google Sheets حقيقيان)**: **لم يُشغَّل عبر كامل هذا
  المشروع حتى تاريخه.** راجع `docs/security-risk-report.md` (البند 12) للتفصيل الكامل حول ما لم
  يُتحقَّق منه بعد (حدود `CacheService` الفعلية، أذونات نشر الـWeb App، صلاحيات مشاركة الشيت نفسه).

## 18) القيود الأمنية الحالية

- المصادقة معطَّلة افتراضيًا (`auth_enabled=0`) — يجب تفعيلها يدويًا قبل الاستخدام الفعلي.
- تجزئة كلمات المرور SHA-256+Salt (وليست bcrypt/Argon2) — مناسبة لأداة داخلية محدودة المستخدمين، وليس
  بمستوى أمان بنكي.
- مدة الجلسة 6 ساعات (21600 ثانية) كحد أقصى نظري، بلا ضمان بقاء الكاش كامل هذه المدة.
- لا شيء يمنع تعديل جدول Google Sheets يدويًا مباشرة (خارج التطبيق) من طرف من يملك صلاحية تحرير الشيت
  نفسه — قيد بنيوي في أي نظام مبني على Google Sheets كمصدر حقيقة، وليس عطلًا في هذا الكود.
- لم يُتحقَّق من أي شيء على منصة Google حقيقية (راجع القسم 17).

التفصيل الكامل (14 بندًا، مع الخطورة والأثر لكل واحد) في `docs/security-risk-report.md`.

## 19) خطوات ما قبل الإنتاج

1. نشر `appsscript/Code.gs` كـWeb App حقيقي على Google Apps Script والتحقق يدويًا من نجاح تسجيل
   الدخول/انتهاء الجلسة/الصلاحيات الأساسية عليه فعليًا (لم يحدث بعد — إلزامي).
2. مراجعة إعدادات مشاركة جدول Google Sheets نفسه وتقييد من يملك صلاحية تحريره المباشر.
3. تفعيل `auth_enabled=1` من تاب الإعدادات.
4. إنشاء أول حساب Administrator عبر شاشة Bootstrap.
5. فحص أي بيانات موظفين حالية (لو وُجدت من نسخة سابقة) بحثًا عن قيم "فروع" فارغة أو غير صالحة قبل
   الاعتماد النهائي (راجع `docs/security-risk-report.md`, البند 3).
6. تشغيل `npm run test:all` والتأكد من نجاح كل الاختبارات محليًا كخطوة تحقق إضافية قبل النشر.

## 20) خطوات رفع المشروع إلى GitHub

1. التأكد من عدم وجود أي رابط Web App حقيقي، كلمة مرور، أو بيانات تشغيلية فعلية داخل أي ملف بالمستودع
   (راجع تقرير فحص الأسرار المُعَدّ عند تجهيز الحزمة النهائية).
2. التأكد أن `.gitignore` يستبعد `node_modules/`، نتائج Playwright، وأي ملف نسخة احتياطية/بيانات
   إنتاجية حقيقية.
3. `git init` (إن لم يكن موجودًا) → `git add .` → مراجعة `git status` يدويًا قبل أول commit للتأكد من
   عدم وجود ملف غير متوقَّع.
4. إنشاء مستودع خاص (Private) أولًا، وعدم جعله عامًا (Public) إلا بعد قرار إداري صريح منفصل.
5. لا رفع تلقائي — هذه خطوات يدوية يقوم بها المسؤول بنفسه.
